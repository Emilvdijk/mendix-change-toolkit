# Reading a Mendix model: which tool for which fact

**House assumption: Studio Pro is open on the project, always.** Every tool here is chosen on
that basis. The one thing it does not buy you is history — see §5.

Four readers exist and **not one of them is complete**. This file records what each actually
returns, measured, and which to reach for. Nothing here is taken from a help text.

> **These are properties of Mendix 11.12.4**, with mxcli v0.26.0 and mxlint v3.18.0 — not of the
> tools in general. Every gap below is a gap *on these versions*, and both CLIs move fast: the
> v0.24 → v0.26 re-measure closed **eight** of mxcli's nine missing flags, and showed two further
> claims in this file to have been wrong rather than merely stale. Treat this as a dated
> measurement, not a specification, and re-probe before trusting it on a different version.
>
> What is still in doubt is tracked in [OPEN-QUESTIONS.md](OPEN-QUESTIONS.md) — row 10 is this
> file's, and it is now narrower: everything here is measured on **11.12.4**, nothing on 11.15.
> The layout findings have moved again; see §33 of `WRITING-TO-THE-MODEL.md`, which states what
> in them expired rather than reversed.

The mxcli and mxlint columns were measured 2026-10-02 on **mxcli v0.24.0** and **re-measured
2026-10-20 on mxcli v0.26.0** (built 2026-10-11), with mxlint v3.18.0 unchanged across both. The
projects: a production ERP app (`<app>.mpr`, Mendix **11.12.4**, 42 modules, 998 microflows, 231
pages, 15,044 activities) with Studio Pro open on it, and a second 14-module app on the same

**The MCP column still dates from 2026-10-02** — the Studio Pro 11.12 MCP server on

## 2. What this means in practice

**mxcli is the default for reading anything, and on v0.26 it is very nearly sufficient alone.**
Logic, pages, entities, access rules, relationships — and, new since v0.24, every document and
activity flag a review actually turns on. One call, complete, and for pages the only practical
option: mxlint's export of the largest page here is 27.6 MB and the MCP returns 211 bytes of
`"..."`.

**What is left for the MCP is a short list, and none of it is load-bearing for a review:**

`markAsUsed` · `includeLatestStackTrace` on a log activity · and on a REST call,
`errorResultHandlingType`, `useRequestTimeOut`, the proxy settings, plus the import-mapping
call's own `commit` and `forceSingleOccurrence`.

Everything else this section used to send you there for — `allowedModuleRoles`,
`applyEntityAccess`, `allowConcurrentExecution`, `excluded`, `documentation`, and per activity
`commit`, `refreshInClient` and `errorHandlingType` — mxcli now renders as MDL. §6 has the
evidence for each.

**Do not use the MCP to read logic or pages.** It expands one level per call — "children are
stubs; re-read child paths to expand further", in its own words. A 21-activity microflow costs
25–40 round trips through it and still arrives in storage order rather than execution order. A
page costs hundreds and never finishes being useful.

**mxlint is now a narrow tool**, given Studio Pro is always open. Three things keep it: it is the
only reader that puts every property of a document in one artifact, it is what `build-history.sh`
replays to make commits diffable, and it is the only reader besides `usages.js` that resolves a
snippet's placement on a layout the app owns. For a question about the current model, mxcli beats
it on latency and size by two to three orders of magnitude.

**sweep.sh** stays the tiebreaker, the only source of sequence-flow edges across a diff, and the
only way to find a snippet placed on a **marketplace** layout — which mxlint never exports.

### The MCP is the only reader that sees the model you are looking at

**Measured 2026-10-02, and it overturns the obvious reading of the matrix above.** While Studio
Pro is open and being edited, the files on disk lag the live model — so mxcli and mxlint are
answering about a state that no longer exists.

The test: two `log` activities added to `Sales.BCO_Customer` in Studio Pro, one saved, one not.

| | On disk (`.mxunit`) | Live model (MCP) |
|---|---|---|
| `LogMessageAction` count | **1** | **2** |
| Message text | `EDIT\n` | two full multi-line messages |

`mxcli describe` rendered one log activity with the text `EDIT\n`. The MCP returned both
activities with their real text. Decoding the `.mxunit` on disk confirms the disk genuinely holds
only one.

**The trap is that this is not a clean saved/unsaved boundary.** Studio Pro *had* written the
`.mpr` 80 seconds earlier, and git saw both the `.mpr` and the unit as modified — so disk was
neither the last commit nor the current model, but a partial state somewhere between. You cannot
tell from a file timestamp, from `git status`, or from the content itself whether what you are
reading is current. In the same session the `.mpr` had also sat **68 minutes** without a write
while Studio Pro was open.

So, with Studio Pro open:

- **mxcli and mxlint read the last write, not the model.** For logic and page structure they are
  still the only practical tools — but their answer may be stale by an unknowable amount.
- **The MCP is the authority on current state.** If a conclusion depends on the document being
  exactly as it is on screen — a bug that reproduces now, anything the developer just changed —
  confirm it through the MCP or ask them to save first.
- **Asking them to save is the cheap fix**, and worth doing before any bulk read.

For a historical commit none of this applies: the worktree is not open in Studio Pro, so disk is
exactly the commit.

### The MCP also has capabilities that are not in the matrix at all

Because none of them are reads of the model:

| | Why nothing else has it |
|---|---|
| **`ped_check_errors`** | Runs **Studio Pro's own consistency check** against the live model, per document. mxcli's `check` validates MDL scripts and `lint` runs rule packs; neither is Studio Pro's validator. Returns `No errors found.` or just the failing documents |
| **`search_mendix_knowledge_base`** | Official Mendix documentation, retrieved and ranked. One query on OQL view entities returned **56 KB** including the View Entities refguide page. Neither CLI ships docs |
| **`read_skill`** | Mendix's **own authoring conventions**, maintained upstream — `microflow-common` is 5.5 KB of naming rules, happy-path/alternative layout and spacing formulas. There is no other copy of this |
| **`oql_generate`** | Generates OQL against a named module's real domain model; with `documentName` it writes straight into a `ViewEntitySourceDocument` |
| **Writing the model** | 6 tools. The only agent-driven authoring path that exists. Out of scope for this read-only toolkit, but it is the headline capability |

So the division is cleaner than "which reader is best": **mxcli and mxlint read the model; the MCP
validates it, documents it, and changes it.**

### Settled: the MCP sees unsaved work, the CLIs do not

Previously open; tested 2026-10-02 and recorded above. The answer is yes, and the staleness has
no reliable tell — see the table at the top of this section.

## 3. The maximum-fidelity read of one document

Two calls, and on v0.26 a third only for the residue in §2.

```bash
# 1. The backbone. Logic in execution order, expressions inline, captions, annotations.
mxcli describe microflow <Module>.<Doc> -p <app>.mpr
#    …or: describe page / entity / nanoflow / workflow — same command, same completeness.
```

```bash
# 2. Relationships. Nothing else gives this.
mxcli context <Module>.<Doc> -p <app>.mpr --depth 2
```

First run builds the whole-project catalog (40-odd tables, 15k activities) and is slow; later
runs reuse it. `mxcli -c "refresh catalog full"` after the project is edited.

**3. The residue — MCP, one or two calls.** Only the flags §2 still lists: `markAsUsed`, a log
activity's `includeLatestStackTrace`, and the REST error-result, proxy and mapping-call
settings. Everything else mxcli renders in step 1.

```
ped_read_document { documentType: "Microflows$Microflow", documentName: "<Module>.<Doc>" }
```

Ignore the stub arrays; read only the flags listed in §2. Then, if the question turns on a
property mxcli does not render, for the activities that *write*:

```
ped_read_document { ..., paths: ["/objectCollection/objects"] }          # locate them
ped_read_document { ..., paths: [".../29/action", ".../30/action"] }     # one batched call
```

Batch every path into a single call. Only read activities that write — `ChangeObjectAction`,
`CreateObjectAction`, `DeleteAction`, `ChangeListAction` — plus whatever the question is about.

**Confirm the open project first.** `list_modules` is one cheap call and its module list is
unmistakable. The MCP answers about whatever Studio Pro has open, with no indication that it is
a different project from the one you were asked about.

### Step 3 is now mostly optional

On v0.24 this section argued the opposite, with this example. mxcli rendered:

```
change $Invoice (SendAt = [%CurrentDateTime%], CountSentEmails = ... + 1);
```

which reads as "it sets these", while the MCP said `"commit":"No"` of the same activity — an
in-memory change the caller must commit. A review that stopped at mxcli stated the opposite of
the truth, and mxcli had no way to express the difference in any output format.

**v0.26 expresses it.** That activity now describes as:

```
change $Invoice (SendAt = [%CurrentDateTime%], ...) commit refresh;
```

and an uncommitted one carries neither keyword. Error handling arrives as
`on error without rollback begin … end error`, a disabled activity as `@excluded`, execute roles
as a trailing `grant execute on microflow …`. Step 3 is now worth a call for two reasons only:
the residue listed in §2, and the case where the model on screen may be ahead of disk.

## 4. Entities: mxcli does security here too

Since v0.26 mxcli renders microflow execute roles as well (§6), so there is no security gap left
between the two. Entity access it has always given in full, including the XPath on each rule:

```
grant Sales.Editor on Sales.Invoice (create, delete, read (…), write (InvoiceNumber))
  where '[Status = ''Processed'']';
```

Attributes arrive with types and defaults in the same call (3,709 B for `Sales.Invoice`,
16 attributes, 5 grants). Do not reach for mxlint or the MCP for a domain-model question.

## 5. The one thing an open Studio Pro does not buy you: history

**The MCP reads the working copy and nothing else.** It cannot read a commit, a detached
worktree, or a range — and no amount of having Studio Pro open changes that.

So every skill that analyses a *range* works exactly as before, with no MCP step:

| Skill | Reads | MCP |
|---|---|---|
| `mendix-review` | a commit range | ❌ unavailable |
| `mendix-test-instructions` | a commit range | ❌ unavailable |
| `mendix-change-notes` | a commit range | ❌ unavailable |
| `mendix-change-report` | a commit range | ❌ unavailable |
| `mendix-plan` | the current model | ✅ use it |
| `mendix-scout` | the current model | ✅ use it |
| `explain-mendix-doc-complete` | the current model | ✅ use it |

A further trap: the working copy is **ahead of or behind** the commit you may be reasoning
about. If the question is "what changed in TICKET-711", the MCP's answer describes neither the
before nor the after. Use it only for questions about the model as it stands right now.

## 6. Claims that were true and are now false

Two re-measures are folded in here: v0.16 → v0.24 on 2026-10-02, and v0.24 → v0.26 on
2026-10-20. **Do not carry an older note forward from either.**

### Closed on v0.26: eight of mxcli's nine missing flags

§2 used to list nine flags mxcli could not render. Eight of them it now does; `markAsUsed` is the
only one left. Each row below was re-run on 2026-10-20 against a document that actually carries
a non-default value — except the last, which is read from the tool:

| Flag | What mxcli v0.26 emits | Measured on |
|---|---|---|
| `allowedModuleRoles` | `grant execute on microflow M.D to M.Administrator, M.Editor;` as a trailing statement | `describe microflow Billing.SUB_Invoice_Save` |
| `allowConcurrentExecution` | `disallow concurrent execution error message '…'` as a header clause | `Sales.SUB_InvoiceNumber_GenerateNext` |
| `commit` / `refreshInClient` | `change $X (…) commit refresh;` — either keyword alone, or neither | `Billing.SUB_Invoice_Save` |
| `errorHandlingType` | `… on error without rollback begin … end error;` on the activity that may fail | a REST call in the 14-module app |
| `excluded` — **document** | `@excluded` before `create or modify microflow` | `Scheduling.ASU_Template_Import` |
| `excluded` — **activity** | `@excluded` before the statement | `Ledger.SUB_Attachment_CreateOrUpdate`: **5** `Disabled: true` in the mxlint YAML, **5** `@excluded` in the MDL |
| `documentation` | `/** … */` doc comment before the statement | `describe constant Jobs.Conf_BatchProcessNotify`, `describe scheduledevent Jobs.SE_ProjectStatusUpdate` |
| `applyEntityAccess` | `@applyentityaccess` / `@applyentityaccess(false)`, document-level | ⚠️ **read from `mxcli syntax`, not measured** — no document in either project has a non-default value |

**The activity-level `@excluded` is the one to know about**, because it is easy to conclude the
opposite. mxlint calls the property `Disabled`; mxcli calls it `@excluded`. Grepping an MDL
describe for "disabled" finds nothing, which reads exactly like a gap — and a disabled activity
reported as live is a worse error than a missing flag.

Closed too, but by a different command than the old note blamed:

- **Which user roles hold a module role.** `refs <Module>.<Role>` still answers
  `(no references found)` on v0.26. `describe userrole <Name>` lists `ModuleRoles: (…)` in full,
  along with `ManageAllRoles` and `CheckSecurity`. The gap was in `refs`, not in mxcli.

### Two claims in this file were WRONG, not stale

Both were recorded as new findings on 2026-10-02, and both are the wrong generalisation of a
real observation.

- **"mxlint truncates long filenames" — no: long *paths*.** Exported into a deep scratch
  directory, dozens of files arrive as `SUB_Something_TRUNCATED_53e69_icroflow.yaml` and mxlint
  logs `Path exceeds safe length (207 chars) … Adjusted path from 207 to 203`. The same project
  exported into a short path truncates **nothing** — longest filename 64 characters, intact. It
  is a Windows MAX_PATH artifact of where you point `modelsource`, not a property of mxlint's
  naming, and `app.yaml` carries `originalName` for every file either way. Point `modelsource`
  somewhere short and the problem does not exist.

- **"No layouts reach the mirror" — only marketplace ones.** The v0.24 note said mxlint exports
  zero layouts, and left "would it export a layout in an app's **own** module?" untested. It
  would, and it does: the 14-module app owns `Shell.TopBar` and mxlint wrote it as a 107 KB
  `Forms$Layout.yaml`, including the line `Form: Widgets.Snippet_Weather`. So **mxlint answers a
  question mxcli cannot** — `refs` on that snippet still says `(no references found)` while
  `usages.js` confirms the placement is real. The original observation holds for the ERP app,
  where all 33 layouts live in marketplace modules and none is exported; it was never a property
  of mxlint.

### Fixed between v0.16 and v0.24 — still true on v0.26

- **mxcli can edit layouts. This is a v0.26 change and it is read from the tool, not measured.**
  Every "a layout is a person's job" statement in this toolkit was written against v0.24, where
  the only layout verb was `alter layout … drop widget <id>`. v0.26 gives `ALTER LAYOUT` the full
  `ALTER PAGE` operation set, makes `DESCRIBE LAYOUT` emit a re-executable `CREATE LAYOUT`, and
  adds `ALTER PAGES … SET LAYOUT … WHERE LAYOUT = …` for repointing pages in bulk. Renaming a
  layout is still impossible and a rewrite is still only as complete as its describe. The full
  revision, with what expired versus what reversed, is §33 of `WRITING-TO-THE-MODEL.md`.

- **Multi-clause XPath truncation is FIXED.** mxcli renders every clause:
  ```
  retrieve $InvoiceList from Sales.Invoice
      where [Status = Project.ENUM_Invoice_Status.Processed]
      [SendAt < $ReminderOffset];
  ```
  mxlint is no longer the XPath tie-breaker.

- **`mxcli diff-local` is no longer broken.** v0.16 failed on every ref; v0.24 connects and
  reports cleanly. Checked against a clean tree only, so the scripts here stay the trusted path.

- **The MCP is NOT good at pages.** An earlier draft of this file said `pg_read_page` returns a
  usable widget tree in one call because it accepts `depth` and `paths`. Measured, it does not:
  the full-page read is **211 bytes** with every widget list elided to `"..."`, and `depth` only
  truncates further. `mxcli describe page` returns the real tree.

### Still true, re-confirmed on v0.26

- `mxcli describe module X` emits only `create module X;` plus module roles — **79 bytes** for a
  module holding 8 microflows, 3 entities and 2 pages. MDL is per-document.
- **mxlint drops `Flows:` entirely.** Zero occurrences in every microflow YAML of both projects.
  Its only ordering is the flat `pseudocode` scalar, which uses `GOTO L003` labels and elides
  action bodies to `// action: Microflows$DeleteAction`.
- **mxlint skips marketplace modules** on export: **21** `Ignoring appstore module` lines on the
  ERP app, 8 on the small one. mxcli reads them — `show snippets` lists Atlas_Core's and
  `graph-report` ranks them among the god nodes.
- **`mxcli refs` and `mxcli impact` do not index snippet-call placement.** Re-measured on v0.26
  against a snippet placed on a layout the app owns: both answer `(no references found)`, while
  `usages.js` finds the `Forms$SnippetCall.Form` property in about a second. The silence is
  convincing because the same commands *do* resolve microflow calls and widget actions
  correctly. This closes OPEN-QUESTIONS row 6 as **not fixed**.
- **`mxcli SEARCH` is a string search, not a usage search.** `SEARCH 'Snippet_Weather'` returns
  the literals *inside* that snippet and nothing that references it.
- **mxlint names page files `Forms$Page.yaml`**, not `Pages$Page.yaml`.

### Carried from v0.24, not re-run

- **`mxcli describe` auto-detect does not know layouts.** A bare qualified name answers
  `no describable document named ...` — indistinguishable from "this type cannot be described" —
  while `describe layout <Module.Name>` returns the whole thing. That one missing word was enough
  to make `mdl-diff.sh` report a marketplace layout as unreadable; it now takes `<type>:<name>`.
- **Nothing can rename a layout.** `mxcli rename` has no layout type, and over the MCP
  `Pages$Layout` and `Forms$Layout` are unknown document types, `ped_list_folder` does not list
  the layout, and `pg_read_page` answers `Page not found`. A layout copied in Studio Pro keeps
  the name Studio Pro gave it (`<Name>_2`) until a person renames it there — which is also the
  only thing that updates the references to it.

### The export has got more expensive, not less

A full export of the ERP app now takes **48.3 s** and writes **1,470 files, 274 MB** — against
**18.5 s**, 1,411 files and 269 MB on 2026-10-02, on the same mxlint version. The project gained
a module in between, which does not obviously account for a 2.6× slowdown; the cause is not
measured. Either way it is the real cost of the mirror `build-history.sh` maintains, and the
reason an export is not something to reach for casually when Studio Pro is open.

## 7. mxcli commands this toolkit does not yet use

All read-only. The list was written against v0.24; the entries marked **v0.26** are new and have
not been tried here:

- `graph-report` — god nodes, coupling, cohesion, dead code.
- `structure` / `project-tree` — compact project overview, JSON.
- `report` — best-practices report. `lint` — mxcli's own linter.
- `describe` now covers `queue`, `scheduledevent`, `regularexpression`, `restclient`,
  `odataclient`, `odataservice`, `imagecollection`, `buildingblock`, `projectsecurity`,
  `modulerole`, `userrole`, `settings`, `demouser`, and the Mendix 11 AI documents — `agent`,
  `aimodel`, `knowledgebase`, `consumedmcpservice`, `datatransformer`.
- `mcp capabilities --mcp <url> -p <app>.mpr` — asks the connected Studio Pro what it can author.
  Quote it in bug reports rather than a version number.
- **v0.26** `changelog` — the release notes, offline, out of the installed binary. This is the
  cheapest way to find out what moved since a note in these files was written, and it is where
  §33 of `WRITING-TO-THE-MODEL.md` came from.
- **v0.26** `syntax [topic …]` — the MDL reference from the feature registry, `--json` for a
  machine read. `mxcli syntax layout` is what revised §22. Ask it before believing any capability
  claim in these files, this line included.
- **v0.26** `diag session-report` — where an agent session's calls and tokens went, read from its
  own Claude Code transcript. Relevant to Dash, which has the transcripts.
- **v0.26** `describe structure depth 2|3` — now lists each page's data widgets.

## 8. Safety

**Everything above is read-only, and it must stay that way.**

- Only these mxcli verbs: `describe`, `context`, `callers`, `callees`, `refs`, `impact`,
  `search`, `show`, `structure`, `project-tree`, `graph-report`, `report`, `mcp capabilities`,
  `refresh catalog`, `changelog`, `syntax`. **Never `exec`, `fix`, `rename`, `layout`, `new`,
  or any MDL write.** (`layout` here is the subcommand that rearranges a domain model, which
  writes. It is unrelated to `ALTER LAYOUT`, which is MDL and also forbidden here.)
- **The allowlist is the whole guarantee, so it must stay closed as mxcli grows.** v0.26 ships
  verbs that leave the model entirely: `auth` (platform credentials), `git` (including
  `git note --write`), `docker`, `tunnel-hub` (a public ingress relay), `catalog`,
  `marketplace`, `run`, `test`, `debug`, `sql`, `oql`, `playwright`, `serve`, `theme`,
  `skill`, `init`, `add-tool`. None of them is read-only-against-the-model in the sense this
  file means, several touch credentials or the network, and `git` collides head-on with the rule
  that no toolkit run goes near a remote (§33 of `WRITING-TO-THE-MODEL.md`). Enumerate what is
  allowed; never subtract from what is not.
- **Never pass `--mcp`.** It routes model writes into the running Studio Pro. mxcli's own `mcp`
  subcommand prints `WARNING: This is a vibe-coded PoC, alpha quality, use with caution.` on
  every invocation — believe it.
- Of the MCP's 18 tools, **6 write**: `ped_create_document`, `ped_update_document`,
  `ped_create_module`, `pg_patch_page`, `write_file`, `install_marketplace_module`. Any automated
  route to this server must allowlist the read tools **by name** and fail closed — never
  allowlist the server.
- **mxcli reads are safe while Studio Pro is open** — which is the standing assumption here.
  `mxcli mcp capabilities` states "Reads … always available from the local .mpr", and the `--mcp`
  design assumes exactly that pairing. mxcli *writes* while the project is open stay forbidden.
- mxlint `export` is read-only against the `.mpr`, but it **writes a `modelsource/` tree**. Point
  it somewhere scratch via a config file rather than letting it land in the project.
- **Local git only. Never `fetch`, `pull`, `push` or `ls-remote`.** A Team Server remote wants a
  credential an agent does not have, and the Git Credential Manager answers by opening a **GUI
  dialog** — so the command *hangs* rather than fails, which from outside is indistinguishable from
  a slow read. `GIT_TERMINAL_PROMPT=0` does not prevent it; that suppresses the terminal prompt,
  not the window. `status`, `log`, `rev-parse`, `diff` and `show` against what is already cloned
  are all fine and are the only git this toolkit needs. If a checkout turns out to be behind, say
  so and stop — a person pulls, in Studio Pro. Measured 2026-10-11; see WRITING-TO-THE-MODEL §32.

## 9. Connecting the MCP

Studio Pro: **Preferences → AI → MCP Server**. Port defaults to 7782 (auto-selected from 11.13).

Register it at **user scope**, not project scope. An agent launched against a Mendix checkout
has that checkout as its working directory, so a server scoped to some other project is invisible
to it — `claude mcp list` run from the checkout simply does not list it.

```bash
claude mcp add -s user mendix --transport http http://localhost:7782/mcp
```

Three things that will otherwise waste your time:

- **The URL hostname must be `localhost`, never `127.0.0.1`.** Studio Pro registers its prefix
  with Windows http.sys under the literal hostname `localhost`, and http.sys matches on the Host
  header, so the IP form is rejected before anything MCP-aware sees it. Measured on the same
  endpoint, same instant: `Host: localhost` → **HTTP 200**, `Host: 127.0.0.1` → **HTTP 400 Bad
  Request — Invalid Hostname**. The failure names the hostname, which is easy to read as a
  networking problem rather than a string-matching one.
- **mxcli's `--mcp-dial 127.0.0.1:7782` is the exception, and not a contradiction.** It overrides
  only the TCP address dialled and leaves the URL — and therefore the Host header — as
  `localhost`. Use it when mxcli's Go resolver sends `localhost` to the LAN address and hangs
  (`dial tcp <your-LAN-ip>:7782: i/o timeout`). Never put the IP in the URL itself.
- **Tools do not appear in a session that was already running** when you added the server.
  `claude mcp list` says `✔ Connected` and the tools still are not there. Start a new session.

The listener is registered with Windows http.sys on **`0.0.0.0:7782`**, not loopback, and exposes
write tools into an open project with **no authentication**. On an untrusted network, turn it off
when you are not using it.
